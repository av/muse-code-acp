# SDK task execution interrupted by repeated approvals — attribution incomplete

Why: Users cannot finish an explicitly delegated multi-step task unattended because successive tool calls stop at Allow once / Reject with no supported session-wide approval mode.

Estimate: 30–60m for triage and linking regression requirements to existing m25; implementation belongs to that multi-task milestone.

## Reproduction and observed behavior

1. Use `@bex-co/muse-code-acp@0.4.0` with the default SDK backend in Bex.
2. Submit: `bump muse spark acp's version and try with it to scan a small directory and ensure it works`.
3. The screenshot shows command steps including registry inspection, dependency checks, package-manager availability, and lockfile inspection.
4. At `Confirm lockfile is now out of date`, the UI offers only `Allow once` and `Reject`, with `Awaiting Confirmation`. The user reports repeated interruptions across the task.

The screenshot establishes a pending one-shot approval; the repeated-prompt behavior is user-reported and was not independently replayed while filing. The environment previously used Muse 1.2.1-R2847.1, unsupported by adapter 0.4.0; separate host compatibility from approval-policy behavior during reproduction.

## Findings and existing blocker

- `src/muse-sdk-host.ts` requests `onRequest` both at session creation and on resume.
- `src/acp-agent.ts` filters SDK session modes to `default`, `readOnly`, and `plan`. `MUSE_CODE_ACP_ALLOW_YOLO=1` does not expose YOLO in SDK sessions.
- `src/muse-permissions.ts` maps only host-provided approval choices and scopes. Bex cannot infer a persistent grant from an `allow_once` option.
- [m25 — Verified SDK approval policies and sandbox configuration](../w1/m25/README.md#enforcement-blocker-2026-09-12) already owns implementation. Its supported-host probes found that `allowAll` was accepted as effective state but the tested shell action still requested approval; changing the enum alone is not a verified fix.
- See also `docs/ADR003-followup-research.md` for the public policy-selection API and separate host-lifetime sandbox controls.

## Expected behavior

Provide an explicitly selected continuous-execution mode whose actual approval behavior is verified. Distinguish automatic approval with sandbox retained from a broader YOLO preset that also changes sandbox posture. The user's choice must have a clear scope and survive the intended session lifecycle without silently resetting to `onRequest`.

If the supported host cannot implement that behavior, expose the limitation clearly rather than advertising a nonfunctional mode or claiming that an environment variable fixes SDK approvals.

### Root cause and breadth

1. **Adapter configuration, confirmed in current source:** SDK session startup sets
   `approvalMode: onRequest`; every cold resume explicitly sets onRequest again.
   There is no requested/effective policy in the exposed session configuration.
   SDK mode advertisement and selection filter out both bypassApprovals and yolo.
   This is shared by SDK clients, but onRequest alone is not a defect: Codex's
   auto-review mode also uses on-request with a different reviewer. The screenshot
   does not establish a previously selected automatic policy or which component
   failed to apply one. Not every tool call necessarily requests approval.
2. **Host enforcement limitation, freshly reproduced:** the public host accepts
   allowAll at startup but still requests approval for the tested unmatched shell
   write. Changing the enum alone is not a verified continuous-execution fix.
3. **Not an established option-mapping bug:** `choicesToPermissionOptions` maps
   actual host session/localPersistent grants to ACP allow_always. The adapter
   does not discard a host session grant merely to force allow_once. The screenshot
   alone cannot establish whether the host offered broader choices; inspect the
   actual public request before attributing a missing button to Bex.
4. **Versions matter:** the report used an unsupported 1.2.1 host. The new probe
   below uses supported 1.1.1 and establishes a related enforcement problem there;
   it does not independently reproduce every step or approval in that Bex session.

## Codex parity implementation and corrected attribution — 2026-09-13

The user requested following codex-acp's native policy architecture and shipping
changes. Its Mode selector appears in both configOptions and legacy modes; native
Codex owns `auto_review` and `never` enforcement, and residual requests are forwarded.
Muse's pinned public MSP has no corresponding reviewer-selection field. Do not
substitute adapter-side unconditional approvals or label allowAll “Approve for me”.

Delivered interface correction: Mode is now included in every session config
response, both setters share validation and persistence, and `/plan` and explicit
mode changes publish both representations. SDK modes remain default/readOnly/plan;
exec-only bypass modes are filtered centrally. Model/effort updates retain Mode.
This removes a configuration discoverability gap for config-option clients; the
original screenshot does not prove this gap caused the reported interruptions.

Fresh isolated probes on Muse 1.1.1-R2514.1 / SDK 0.1.1 found:

- `pwd`: zero approval requests with either onRequest or allowAll.
- `write_file` creating `policy-marker.txt`: zero approvals and actual file creation
  with either mode. This does not establish a distinct allowAll capability.
- `printf allowed > policy-marker.txt`: allowAll reported as effective, but one
  unresolved shell-stage request remained, with protectedWrite=false and
  judgeEscalated=false. Explicit fixture rejection left the marker absent.
- `muse --disable-approval serve` is rejected as invalid TUI options. Root TUI flags
  cannot be used as serve approval configuration; serve help requires wire selection.

The pending native-policy investigation remains m25/t001. Inspect the original
Bex selection and wire trace before assigning a client/adapter fault; separately
establish the host's actual enforcement for ordinary, compound and file-tool
operations. This change does **not** close 003 or establish uninterrupted execution.

Validation: build, lint, format and packed-install smoke passed. The real-host
