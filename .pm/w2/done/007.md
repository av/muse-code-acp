# 007 — Evaluate observing raw MSP notifications instead of polling the fold

Why: the adapter can only see what it remembers to poll, and a decision to keep it that way should
be recorded deliberately rather than inherited.

Phase 3 of the systematic design agreed on 2026-09-13, deferred out of [m1](m1/README.md).

`MuseClient` claims `Connection.onNotification`, which holds exactly one handler, and its own source
says a consumer needing the raw feed should build on a bare `Connection` and `Session` instead. So
today the adapter's only control-plane inputs are the SDK's handlers plus whatever it polls from the
fold. m1 made polling the approval path work and added a stall bound, which removes the urgency;
this note is about whether the structure should change.

Taking the raw feed would give every `SessionApplyOutcome` directly, so an unconsumed frame could be
observed rather than inferred. The cost is real: the adapter would own `session/closed`, host-death
discharge and gap-fill triggering, which `MuseClient` handles today and which
[w1/m6](../../w1/done/m6/README.md) and m10 already have working.

A cheaper middle option exists and should be priced first: a read-only tap on the child's stdout,
which `spawnMspConnection` already exposes, counting methods and warning once for any method the
adapter has never classified. That covers "a newer host sent something we do not know about" without
taking ownership of the connection lifecycle.

Deliverable is a recommendation with a cost estimate, not an implementation. Closing this as
"keep polling, add the tap" is a valid and probably the expected outcome.

## Recommendation (2026-09-14)

Keep MuseClient and fold polling. Use the narrow, demand-driven public view/page
read implemented by 006 for durable persistence facts the SDK discards. Do not
replace the router or add a general raw-notification parser in this release.

The initially proposed cheap stdout tap is not exposed by @muse-code/sdk 0.1.1.
The published connection/spawn.d.ts exposes MuseServeChild.exit, stderrTail and
close. Its ChildProcess stdout is reachable only through the module-private
ownedTransport symbol. It is not a supported adapter integration surface.
Connection.onNotification stores one handler and MuseClient claims it; assigning
another observer replaces routing rather than subscribing alongside it.

Options and estimates (engineering estimates, including meaningful coverage):

| Option                                                 | Estimate                                                       | Benefit and cost                                                                                                                                                                                                                                                              |
| ------------------------------------------------------ | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Keep fold observation and targeted view/page reads     | Delivered by 006; roughly 1 hour                               | Preserves SDK lifecycle and decisions. Two current state families are sampled every 100ms. While a selected persistent rule is unverified, at most one 100-event page/second, with a 1s timeout and unavailable latch. Cannot observe nondurable discarded or unknown frames. |
| Add a supported SDK notification observer upstream     | 1–2 days upstream plus 2–4 hours adapter integration           | Best long-term route to method counters, unknown-method warnings and post-fold outcomes; requires a non-owning subscription API and tests that preserve existing routing. No such API is published in 0.1.1.                                                                  |
| Replace MuseClient with Connection and Session routing | 2–4 engineering days plus host-matrix validation               | Exposes SessionApplyOutcome directly, but the adapter must reproduce session seeding/joins, routing, gap-fill entry, close notifications, pending-command retirement and durable/ephemeral host-death discharge. Existing m6/m10 behavior becomes regression scope.           |
| External stdio tee                                     | 1–2 hours for local diagnostics; 1–2 days to productize safely | Already useful under artifacts for isolated repros. Shipping it adds an extra process, framing/UTF-8/size limits, lifecycle and package/standalone obligations. Not justified for reporting alone.                                                                            |

The static method-classification test still detects a changed pinned SDK, while
m1's reconciler and watchdog bound the known liveness defect. This deliberately
does not claim detection of every method a newer host can send. A broad raw tap
would improve diagnostics, not replace requirement reconciliation or approvals.

Reconsider when the SDK publishes a non-owning observer, or a required feature
needs a nondurable fact unavailable through folded state or the durable view.
Unknown-method counting is not implemented and is not required to close this
evaluation-only note. No private API, TUI, new model call or upstream lifecycle
rewrite is part of this recommendation.

Evidence: pinned SDK facade/client.js (single notification handler ownership),
connection/spawn.d.ts (public process boundary), fold/session-fold.js (#23379
post-resolve persistence drop), and the 006 source/tests. The existing read-only
tee under artifacts/w2-m2 verified raw frames without entering production code.

Completed as an evaluation on 2026-09-14. The selected implementation shipped in
`41a1fcd`; no raw tap is added. Formatting and archive-link checks passed.
