# Bug: editor context changes slash-command routing and workflow enforcement

Why: users can receive an opaque rejection, or ordinary model execution instead
of the requested status/planning/review operation, depending on prompt block order.

Reported: 2026-09-13. Status: done (shipped in `d9f509f`). Priority: P1 for dispatch correctness.
Source: wider-impact investigation of [w2/001](001.md), adapter 0.4.1 at `e4e137d`.
Estimate: 2–4h for a shared dispatch contract, behavior coverage and adoption docs;
promote to a milestone before implementation. No implementation is part of this triage.

## Confirmed scope

All six SDK built-ins: `/goal`, `/mcp`, `/plan`, `/review`, `/review-branch`,
`/review-commit`. Both parsers inspect only `prompt[0]`; recognized commands
require exactly one text block. See `src/acp-agent.ts:967` and
`src/review-prompt.ts:14`.

- Command first + embedded text resource: `-32602`, no model turn. The same
  length guard also covers a second text block or image.
- Embedded resource or unrelated text first + command second: not recognized;
  starts one ordinary turn and forwards context. This is not dropped text, but
  lost command semantics.
- `/plan` after context emits no plan-mode change. In a fresh default-mode session
  it does not acquire the plan host restrictions. Review commands after context
  do not prepare the Git snapshot or select the review-specific read-only path.
  Normal sandboxing, approvals and any already-selected mode remain applicable;
  this is not evidence of bypassing those controls or of actual destructive work.
- `/goal` and `/mcp` after context start a model turn instead of local status
  inspection, potentially using provider quota.
- SDK skill names matching built-ins are intentionally shadowed; advertisement
  filters those names. Other skills and unknown slash strings are prompt
  passthrough. `/compact` is not an adapter compaction operation.
- Built-in advertisements supply descriptions but no input hints, including
  `/plan`, `/review-branch` and `/review-commit`. Required-reference commands
  therefore need clearer help; actual editor insertion behavior was not tested.
- Exec does not intercept these six commands; it uses prompt passthrough, not
  equivalent status or guarded workflow behavior.

## Acceptance (completed under the user-approved implementation below)

- [x] Define one explicit command-selection contract for client text and attached
      context. Do not scan resource contents for executable commands, blindly reorder
      ambiguous user text, or discard attachments. Ambiguous layouts must fail clearly
      rather than quietly become a default-mode model turn.
- [x] Cover all six commands with plain text, appended/prepended resource, extra text,
      images, whitespace, invalid arguments, lookalike names and reserved-name skill
      collisions; include exec passthrough expectations.
- [x] Preserve local status operations with zero model turns and verify `/plan`
      mode/host flags and review snapshots whenever a workflow is accepted. If context
      is unsupported, explain how to submit the command safely without dropping it.
- [x] Keep MCP workflow exclusions, busy-turn checks, cancellation, existing selected
      modes and host-provided permission gates intact. Explicit `session/set_mode`
      is currently a more reliable way to enter plan mode than a decorated slash prompt.
- [x] Add command-specific usage and input hints, align help/docs with SDK vs exec,
      and keep unknown slash strings from being described as native control success.
- [x] Run deterministic wire coverage and supported-host workflow acceptance before
      claiming enforcement; coordinate goal messaging with w2/001, native controls
      with w1/002. Do not invent APIs or perform TUI automation.

## Implementation — 2026-09-13

The user approved prioritizing execution over asking users to rewrite prompts.
This supersedes the earlier triage recommendation to reject or merely explain
all goal objectives and ambiguous block positioning. Implementation was shipped to `origin/main` in `d9f509f`.
It remains unreleased on npm; package version 0.4.1 does not contain this fix.

- Shared `src/slash-commands.ts` registry selects explicit command-leading
  top-level text anywhere, preserves attachments and extra instructions, merges
  duplicate operations, and confines mixed requests containing plan to planning.
- `/goal <task>` explicitly explains the persistence limitation and executes once
  in the current mode. Pause/resume/clear/edit stay local unsupported operations;
  no persistent-goal API or automatic loop is fabricated.
- Bare plan changes mode locally. Planning/review task inputs retain all supported
  context; review accepts focus instructions and default HEAD/upstream references.
  Status queries remain local unless separate task text explicitly accompanies them.
- Unit and ACP wire coverage checks actual turn count, context/image retention,
  status behavior, cancellation, invalid attachments and mode selection. Real-host
  workflows now include preceding resources and additional text while checking
  actual denied writes, restart persistence and explicit mode transitions.

Validation: `npm run check` and build passed; final complete unit suite:
332 tests / 54 files passed. Supported Muse 1.1.1-R2514.1 / SDK 0.1.1
real-host suites: 23 tests / 9 files passed, including decorated workflow requests
and actual write denial. Packed-install ACP smoke passed. The concurrently filed
003 note received Markdown formatting only; its approval-policy scope is unchanged.
No real Bex transport capture or production replay was available. Native goal
controls remain a separate upstream capability investigation, not delivered here.
