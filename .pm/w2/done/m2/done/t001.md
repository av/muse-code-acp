## Objective

Establish, for each of the six failures, exactly which public host response the adapter receives, so t002 and t003 fix or record from evidence rather than inference.

## Context

- The failures and their two causes are recorded in this milestone's README. Reproduce with `MUSE_CODE_ACP_REQUIRE_MUSE=1 npm run test:muse-loopback` after `npm run build`.
- The w2/m1 work left a reusable technique for this: a stdio tee around the resolved `muse` binary records every MSP frame in both directions. See `artifacts/w2-004/tee.mjs` and `frames2.mjs` (gitignored) for the shape.
- Isolate every probe: own `HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, loopback provider with dummy credentials. No paid model calls.
- Read `.pm/DO_NOT_DO.md`: probes use public MSP and documented CLI surfaces only.

## Steps

1. Capture MSP frames for one `:auto-review` failure (an `acp-restart-live` load case and the `muse-sdk-live` case), and record where the profile is attached: `session/start` params, the saved session read back by `session/read`, and the exact error frame.
2. Capture frames for one HTTP MCP failure and record what the host reports about the failing endpoint: any `item/*`, tool result text or session state naming the connection outcome, and what the prompt terminal carries.
3. Write the findings into the milestone README under a "Frame evidence" heading: per cause, the observed request, the observed response, and whether any adapter-visible public field could change the outcome.
4. Retain the probe scripts and frame logs under `artifacts/w2-m2/` (gitignored).
