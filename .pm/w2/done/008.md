# 008 — Report the SDK's unrouted `approval/updated` to the Muse SDK project

Why: the defect m1 worked around is in a published SDK, so every other MSP client written against it
has the same silent hang waiting to happen.

`@muse-code/sdk@0.1.1` folds `approval/updated` but deliberately does not route it to the
`onApproval` handler. Its `facade/session.js` explains why: tdd SS5.6.3 says a re-issued
`approval/requested` embodies the refresh. Muse 1.2.1-R2847.1 does not re-issue one; it advances a
multi-stage approval with the update alone. A client that relies on the router therefore answers the
first stage and waits forever, with no error and no timeout. Full evidence, including both wire
traces, is in [m1's Issue cause](m1/README.md).

Two changes would close it upstream, and either alone would have prevented the hang:

- Invoke the approval handler when `currentRequirementId` changes, not only on `approval/requested`.
- Expose `ApprovalDecideResult.terminal` to the handler. The router discards it today, so a
  non-terminal decision is indistinguishable from a completed one — which is exactly why the adapter
  could not detect its own stall.

Roughly 30 minutes: open an issue at the SDK's tracker (`package.json` `bugs`, the `meta-models/muse-code-sdk`
repository) with the two traces, the host version and the minimal reproduction. No repository change
here. Keep it public-safe: use the loopback provider and redact local paths from any attached log.

If upstream fixes this, the adapter's fold-driven reconciler stays correct either way, so there is no
migration to plan; only `docs/sdk-migration.md` would need a note that the router is no longer the
only path.
