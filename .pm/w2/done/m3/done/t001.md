## Objective

Make each staged permission request identify, in a field every ACP client renders, which part of the command it is deciding and how many stages there are.

## Context

- `approvalToPermissionRequest` in `src/muse-permissions.ts` builds `toolCall.title` from `rawInput.description`, then `command`, then `path`, then the tool name. For a staged shell approval every stage produces the same title.
- The host publishes what is needed on the approval subject: per-stage `argv`, `position`, `totalStages` and `resolution.kind`. `ApprovalStage` and `approvalStageMetadata` already model them; `currentApprovalView` already returns the refreshed subject for the stage being decided.
- Only presentation changes here. `optionId` values, choice order, `_meta.museRequirementId` and the opt-in `muse/approval` block stay exactly as they are.
- Guard the single-stage case: an approval with one requirement, or no stage evidence, must render exactly as it does today. Unknown `resolution.kind` values are preserved rather than mapped, matching the existing reviewer-stage behavior.
- `.pm/DO_NOT_DO.md`: derive from host-published fields only. Do not split or re-parse the raw command in the adapter.

## Steps

1. Add a helper beside `approvalToPermissionRequest` that, given the current view, returns the stage entry matching `currentRequirementId.sourceIndex`, or `undefined` when there is no stage evidence or only one requirement needs a decision.
2. When that helper returns a stage, compose the rendered title from its host-published `argv` and `position` of `totalStages`. Keep the whole command reachable in `rawInput` so nothing is hidden from the user.
3. Leave `kind`, `options`, `_meta` and the single-stage title path untouched.
4. Confirm by inspection of a captured frame that two consecutive requests now differ in `title`.
