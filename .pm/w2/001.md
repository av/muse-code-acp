# Bug: `/goal <objective>` rejects the task with an opaque Invalid params error

Why: A user trying to start a persistent goal in Bex receives a protocol error before the task reaches Muse, with no actionable explanation of the supported workflow.

Reported: 2026-09-13. Status: triaged; open (P2 command UX). Source: user report from Bex Desktop's Muse Code agent in the `bex-security` project.

Estimate: 30–60m for command UX triage and regression coverage; verified goal creation support may require a separate milestone.

## Reproduction

1. Open a Muse Code ACP session in Bex using `@bex-co/muse-code-acp@0.4.0` with the default SDK backend.
2. Send this exact input:

   ```text
   /goal bump muse spark acp's version and try with it to scan a small directory and ensure it works
   ```

3. The user reports this error:

   ```text
   Invalid params: Use /mcp, /mcp status, /goal or /goal status without additional content; goal controls are unavailable
   ```

## Actual behavior and evidence

- `src/acp-agent.ts`, `prompt()`, intercepts inputs beginning with `/goal` on the SDK backend. It accepts only `/goal` or `/goal status` as a single prompt content block; the reported objective text fails this validation before model dispatch.
- The exact error was confirmed in the installed 0.4.0 package and exists in this checkout. The original Bex session was not independently replayed during filing.
- `docs/goal-extension.md` intentionally defines observation-only support (`controls: []`). Bare `/goal` inspects state; it does not create a goal.
- The retry environment previously reported Muse CLI 1.2.1-R2847.1, which adapter 0.4.0 does not support. That compatibility issue is separate from this adapter-side input rejection; validate the fix against the supported Muse 1.1.1-R2514.1 host.

## Expected behavior

The user's intended workflow is `/goal <objective>` to create a persistent goal and start work. Investigate whether the supported public SDK/host can deliver that behavior. When it cannot, the command must clearly explain that `/goal` is status-only and tell the user to submit the objective as an ordinary prompt, without claiming a persistent goal was created.

## Acceptance criteria

- [ ] Reproduce the exact input through the ACP prompt path and cover it with a regression test.
- [ ] Provide an actionable unsupported-command response that distinguishes status inspection, ordinary task execution, and persistent goal creation; avoid the unrelated combined `/mcp` usage message.
- [ ] Preserve `/goal` and `/goal status` as observation-only operations without starting a model turn.
- [ ] Cover Bex-style additional context blocks so command handling does not silently drop attached context or task text.
- [ ] If goal creation becomes supported, verify it through a documented API and real-host evidence before advertising success. Natural-language instructions or model tool calls are not guaranteed control operations.
- [ ] Keep slash-command help and documentation consistent with the delivered behavior. If controls remain unavailable, record the blocker and supported alternative explicitly.

## Triage — 2026-09-13

Confirmed on adapter 0.4.1, commit `e4e137d`, SDK 0.1.1, through a spawned
ACP stdio connection with the repository fake MSP host. The exact reported
objective returns `-32602` and starts **zero** model turns. This is an
adapter-side admission decision, not a provider failure or a project-name issue;
0.4.1's documentation-only changes did not fix it.

Keep this note focused on actionable `/goal` help and unsupported controls.
`/goal`, `/goal status`, `/mcp`, and `/mcp status` each completed without a
`turn/start`. `/goal clear` and `/mcp reconnect` receive the same combined,
unhelpful goal/MCP error. Rejecting unsupported control operations is intentional;
the misleading/shared error and missing ordinary-prompt alternative are the UX defect.
Existing goal-wire tests assert the error code for clear, but do not cover the
reported objective or guide the user toward a supported alternative.

**Wider issue:** all six SDK built-ins have order-sensitive multi-block dispatch.
Tracked separately in [002 — Slash-command routing with editor context](002.md),
with higher priority because planning/review semantics can silently disappear.
Do not solve this by silently forwarding `/goal <objective>` to a model and
claiming persistence. Goal-control API reassessment remains owned by w1/002;
this triage adds no new verified native goal-control capability.

Evidence and limits: [40-case wire matrix](evidence/slash-command-triage.md).
No real Bex request capture, provider calls, host upgrade or runtime change was
performed. The multi-block cases are representative ACP layouts, not a claim
that Bex always sends that layout. All acceptance criteria above remain open:
a diagnostic reproduction is not a shipped regression fix.

## Implementation — 2026-09-13

The user approved prioritizing execution over asking users to rewrite prompts.
This supersedes the earlier triage recommendation to reject or merely explain
all goal objectives and ambiguous block positioning. Implementation is in the
working tree; not yet published.

- Shared `src/slash-commands.ts` registry selects explicit command-leading
  top-level text anywhere, preserves attachments and extra instructions, merges
  duplicate operations, and confines mixed requests containing plan to planning.
- `/goal <task>` explicitly explains the persistence limitation and executes once
  in the current mode. Pause/resume/clear/edit stay local unsupported operations;
  no persistent-goal API or automatic loop is fabricated.
- Bare plan changes mode locally. Planning/review task inputs retain all supported
  context; review accepts focus instructions and default HEAD/upstream references.
  Status queries remain local unless separate task text explicitly accompanies them.
- Unit and ACP wire coverage checks actual turn count, context/image retention,
  status behavior, cancellation, invalid attachments and mode selection. Real-host
  workflows now include preceding resources and additional text while checking
  actual denied writes, restart persistence and explicit mode transitions.

Validation: `npm run check` and build passed; final complete unit suite:
332 tests / 54 files passed. Supported Muse 1.1.1-R2514.1 / SDK 0.1.1
real-host suites: 23 tests / 9 files passed, including decorated workflow requests
and actual write denial. Packed-install ACP smoke passed. The concurrently filed
003 note received Markdown formatting only; its approval-policy scope is unchanged.
No real Bex transport capture or production replay was available. Native goal
controls remain a separate upstream capability investigation, not delivered here.
