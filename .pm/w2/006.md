# 006 — Surface session-state changes the adapter currently folds and ignores

Why: the host publishes approval-mode, model and policy-persistence changes that no adapter code
reads, so a client can be told one thing while the session is doing another.

Phase 2 of the systematic design agreed on 2026-09-13, deferred out of
[m1](done/m1/README.md). That milestone classified every view event the pinned SDK folds; three
entries in `IGNORED_VIEW_EVENTS` (`src/muse-view-events.ts`) are marked "phase 2" rather than owned
by another milestone:

- `session/approvalModeChanged` — the effective approval mode can change under the session. The
  adapter selects `onRequest` at start and resume and never observes a later change, so an advertised
  mode and the enforced mode can diverge silently.
- `session/modelChanged` — same shape for the model the session is actually using.
- A failed `localPersistent` policy persistence, which the SDK's own fold comments record as dropped
  (their issue #23379): a user picks an allow-always choice, the host fails to persist the rule, and
  nobody is told. The adapter already only offers allow-always when the host lists it, so the gap is
  in reporting the outcome, not in the offer.

Roughly an hour if it stays reporting-only: diff the relevant `fold.sessionState` families on the
existing poll tick and publish changes as negotiated `session_info_update` metadata, the way host
compatibility is published today. It becomes a milestone if acting on a change is in scope — for
example re-synchronizing the advertised ACP mode when the host changes the approval mode, which
touches `src/modes.ts` and `src/config-options.ts` and needs its own real-host evidence.

Do not start this by reopening `IGNORED_VIEW_EVENTS` wholesale: `session/todoListChanged`,
`session/tokenUsage` and `session/contextUsage` belong to [w1/m9](../w1/m9/README.md) and
`session/branchChanged` is deliberately unscheduled.
